# 开发说明

## 1. 技术栈

| 层 | 选型 | 说明 |
| --- | --- | --- |
| GUI | Python + Tkinter / ttk | 无额外 UI 框架，打包体积小 |
| 拖拽 | tkinterdnd2 | Windows 资源管理器拖入 |
| PDF 渲染 | pypdfium2 | Apache-2.0 / BSD-3-Clause，替代 AGPL 的 PyMuPDF |
| PDF 文字层 | pdfplumber / pdfminer.six | MIT，取 words/坐标解析电子票 |
| OCR | RapidOCR + ONNX Runtime | 本地 PP-OCR 模型，无需联网 |
| 二维码 | zxing-cpp | 读取发票二维码中的号码/日期/金额 |
| 图像 | OpenCV / NumPy / Pillow | 旋转、缩放、数组转换、预览 |
| Excel | xlwt / xlrd | 生成 BIFF8 `.xls`，兼容旧模板/打印 |
| 打包 | PyInstaller | onedir 便携 exe |

目标平台：Windows 10/11 x64。源码建议 Python 3.10–3.12；本项目在 3.14 上测试通过。

## 3. 数据流

```
输入文件/文件夹
  → collect_input_files()            自然排序、去重
  → 逐页选择引擎 decide_engine(mode, is_pdf, words)
     ├─ 电子页（文字层足够）→ pdfplumber extract_words → boxes_from_words()
     │                        → parse_invoice() → merge_discount_lines()
     └─ 扫描页/无文字层/回退 → pypdfium2 渲染 → detect_orientation()
                              → ocr_page_cached() → parse_invoice()
  → decode_qr()                      zxing-cpp，4 个方向都试
  → 文字层失败时 OCR 回退；两边都有时 cross_validate_invoices()
  → dedup / 跳过非发票页
  → assign_sheet_names()
  → write_workbook()                 xlwt 生成 .xls
  → verify_workbook()                xlrd 读回核对
  → export_pdf_and_check()           可选，Excel COM + pypdfium2
```

`process_inputs(..., mode="auto"|"text"|"ocr")`：`auto` 按页判断；`text` 只走文字层；`ocr` 强制 OCR。

## 4. 关键实现

### 4.1 页面渲染与方向

- `render_pdf_page()` 用 `pypdfium2` 的 `page.render(scale=dpi/72)` 渲染，再转成 OpenCV BGR。
- PDF 页面在 300dpi 下渲染用于识别，150dpi 用于方向判断和预览。
- `detect_orientation()` 分别 OCR 0°/90°，根据“电子发票”标题、开票人页脚、关键词数量/置信度综合评分；如果标题在页面下方、页脚在上方，再翻 180°。
- 图片走 Pillow/OpenCV，支持 EXIF 方向修正。

### 4.2 OCR 缓存

- 缓存键：`pdfium|文件绝对路径|文件大小|mtime|页码|旋转角|dpi`。
- 缓存位置：`%LOCALAPPDATA%\Invoice2RKD\cache\<sha1>.json`。
- 文件修改时间变化会自动失效；换渲染库/参数会因键变化失效。
- OCR 返回的 box 统一成 `x0/x1/y0/y1/cx/cy/w/h/t/s`，后续解析只依赖这些字段。

### 4.3 二维码

- `decode_qr()` 对图像做 0/90/180/270 四次尝试，去重。
- 标准全电发票二维码载荷：`01,31,,<发票号>,<价税合计>,<YYYYMMDD>,,<校验码>`。
- `parse_qr_payload()` 提取号码/金额/日期；缺失时回退到 OCR 文本。
- 如果一页出现多个不同发票号，整页跳过并提示拆分。

### 4.4 表头检测与推断

发票版式差异很大，不能要求 8 个表头全部 OCR 成功。`get_headers()`：

1. 先按关键词找：项目名称、规格型号、单位、数量、单价、金额、税率、税额。
2. 至少找到 3 个才进入推断。
3. 用表头下方的数字 box 做 `cx` 聚类，从右往左推断缺失的税额、税率、金额。
4. 如果数量缺失，用 `数量 ≈ 单价cx - (金额cx - 单价cx)` 估计。
5. 如果单位缺失，用规格/数量中点估计。
6. 最后用相邻已知表头中点/外推补齐剩余列。

这让普通发票、专用发票、带印章/水印的扫描件都能落到统一的 8 列坐标上。

### 4.5 合计行

旧版用“金额+税额=二维码总额”找合计行，单张明细发票会和明细行混淆。现在：

1. 先找“价税合计/小写”的 y，作为表格底部。
2. 有二维码价税合计时，优先在带 `¥/￥` 的金额 box 里找“金额 + 同行税额 ≈ 二维码总额”的那一行；电子票和扫描件都适用。
3. 找不到再用“带货币符号且该行没有名称/规格”的金额 box，最后选底部且没有名称/规格的金额 box。
4. 合计税额优先用同一行匹配二维码总额的税额 box；OCR 缺失时用 `二维码总额 - 合计金额`。
5. 合计行不会被当作明细锚点；“合计”两个竖排字不会串到明细名称里。

### 4.6 明细行与单元格

- 以金额列的 box 作为行锚点，按 y 中点分 band。
- 名称/规格归到“最后一个起始位置不高于自己的明细行”，支持一个项目名称折行成多个 box；避免长名称串到下一行。
- 文字层解析用表头左边界修正名称/规格列：长商品名从名称列起笔时整段留在名称列，不再被半路切到规格列。
- 去掉项目名称开头的税收分类前缀：`*金属制品*`、`*生产生活服务*劳务*` 等，支持多个前缀。
- 名称/规格 OCR 缺失末尾字时，可用 `data/completions.json` 或学习库补全。
- 单位按列/行读；如果单位是竖排合并字符串（如 `套您根项`），按行切分并校验；不行则用项目名/规格/学习库推断。

### 4.7 数量 + 单价粘连

扫描/OCR 常把“数量 单价”合成一个 box，甚至丢小数点。`parse_invoice()` 的处理顺序：

1. 数量列有独立 box：直接用。
2. 如果 box 文本是两个完整数字（中间有空格）：取第一/第二个。
3. 如果是 `12 43073988672566` 这种，尝试在第二个数字里插小数点，使 `数量×单价≈金额`。
4. 如果 box 跨数量/单价列，逐字符尝试切分。
5. 拒绝“左边是长小数、右边只有 1 位数字”的切分，避免把单价最后一位当数量。
6. 最后兜底：`数量 = 金额 / 单价`。

### 4.8 金额、税额、价税合计

- 合计金额/税额优先用合计行 OCR；缺失时用二维码总额和明细推算。
- 明细金额/税额来自发票行；税额缺失时用该行税率；税率也缺失时用本发票出现最多的税率（常见 13%/1%）推断。
- `Invoice.finalize_totals()` 做最终平衡：
  - 明细之和与合计差 ≤0.05 时，把差额并到最后一行（发票自身舍入）。
  - 差更大时保留合计，写警告，等人工补行。
- 自检读回 `xlrd`，核对每张表 `金额+税金=含税价`、合计=发票价税合计。

### 4.9 供应商、表名、日期

- 销售方：按视觉行+左右分段找“名称：xxx”；新版电子发票固定取右半边的销售方全称。
  - 支持 `名称：公司名` 合在一起，也支持 `名/称/:/公司名` 被拆成单字的竖排标签。
  - 购买方“个人”、自然人、购买方公司（`data/company.json` 的 buyer）一律排除。
  - 找不到右侧名称时退回“不是个人/不是购买方”的候选；宁可留空并警告，也不把“个人”当卖方。
  - 用历史供应商做模糊纠正。
- 供应商简写：去掉“有限公司/有限责任公司/股份有限公司/（个体工商户）/（个人独资）”等后缀；可在界面覆盖。
- 表名：`简写 + 价税合计`；整数金额不带小数，有角分保留 2 位；重名加 `-MMDD`，再冲突加 `-2`。
- 表名超过 31 字符时优先压缩简写，保留金额。
- 日期默认开票日期；到货/入库日期可全局覆盖。

### 4.10 文字层 + OCR 双路径

- `pdfplumber` 懒加载；未安装时自动只用 OCR，不影响启动。
- `boxes_from_words()` 把 `extract_words()` 的 word 转成与 OCR 相同的 box 结构：
  - `unicodedata.normalize("NFKC", text)` 修正电子票里的康熙部首等异体字。
  - 相邻单字表头（“单”+“位”、“数”+“量”、“金”+“额”、“税”+“额”）按同线小间距合并。
- `text_layer_sufficient()` 用“20 位发票号/发票号码 + 项目名称/金额 + 价税合计/小写”判断是否有可用文字层。
- `decide_engine(mode, is_pdf, words)` 逐页返回 `text / ocr / none`：
  - `auto`：文字层足够走 text，否则 ocr；
  - `text`：强制文字层，没有文字层则 `none`（进程会写明确跳过原因）；
  - `ocr`：强制 OCR；图片永远走 OCR。
- 旋转页（`page.rotation % 360 in (90, 270)`）文字层坐标不可直接复用，按页走 OCR。
- `text_invoice_issues()` 校验发票号、价税合计、明细、销售方、明细金额/税额、负数；有致命问题就回退 OCR。
- `cross_validate_invoices()`：文字层为主，OCR 只补缺失的销售方/号码/日期/合计/明细，并记录冲突警告。
- 二维码始终作为独立校验源：`parse_invoice()` 优先用二维码的号码/日期/价税合计。
- 速度取舍：文字层完全通过校验的页不再额外跑 OCR；出现缺字段/金额不一致/负数等提示时才 OCR 回退并交叉校验。

### 4.11 优惠行合并

`merge_discount_lines()` 在 `parse_invoice()` 最后、`finalize_totals()` 之前执行：

1. `amount < 0` 或 `tax < 0` 视为优惠行。
2. 优先合并到前面最近的、名称/规格相同或相似的整数商品行；匹配不到就合并到前面最近的正数行。
3. `金额 += 优惠金额`，`税额 += 优惠税额`，数量保持正数行数量，`单价 = 净额 / 数量`。
4. 删除优惠行并重新编号；前面没有正数行时丢弃并警告；合并后仍为负则移除该行并警告。
5. 净额可以为 0（例如买一赠一/全额抵扣），但不会输出负金额/负单价。

### 4.12 文字层字段细节

- 发票号：优先二维码；文字层用 20 位数字/“发票号码”回退。
- 日期：优先二维码；文字层按“YYYY年MM月DD日”回退。
- 价税合计：优先二维码；文字层按“（小写）”同行金额回退。
- 合计行金额/税额：按 4.5 的二维码反查规则，比旧版“找最底部 ¥”更稳。
- 名称/规格：按 4.6 的折行归属 + 表头左边界修正；分类前缀 `*xxx*` 仍会去掉。

### 4.13 中/英界面

- `i18n.py` 负责：
  - `system_language()`：Windows 用 `GetUserDefaultUILanguage()` 判断主语言；非中文默认 `en`。
  - `get_language()` / `set_language()`：语言保存在 `%LOCALAPPDATA%\Invoice2RKD\settings.json`。
  - `tr()`：静态文案精确翻译；`tr_runtime()`：日志/警告/动态消息的正则翻译（支持多轮嵌套）。
  - `help_text()`：中/英文使用说明。
- GUI 构建完成后调用 `_apply_language()`：
  - 递归遍历控件，翻译 `text`；单独处理 Notebook 标签、Treeview 表头。
  - 首次翻译时把原始中文记在控件 `_i18n_src`，所以中/英来回切换可以恢复。
  - 模式下拉框、状态条、提示条、语言下拉框单独处理。
- 语言切换立即生效，不需要重启。
- **Excel 模板和打印入库单不参与翻译**，始终中文；这是财务/税务资料要求。软件界面英文只服务于操作者。
- 新增动态文案时，中文写进 `gui.py` 后，应在 `i18n.EN` 或 `i18n.PATTERNS` 补英文。

## 5. Excel 模板

`excel_writer.py` 固定输出 19 行起、13 列：

- A1:M1 合并，标题来自 `data/company.json` 的 `title`（默认“入库单”），宋体 24。
- A2:M2 合并，`收到：<销售方全称>`，宋体 14，左对齐。
- 第 3 行表头。
- 明细默认 13 行；超过则顺延；合计行紧随其后；空一行；页脚行。
- 第 7 列“单价含税”隐藏。
- 金额/单价/税金 2 位小数；合计行金额/税金使用 `0.00_);[Red]\(0.00\)`。
- 名称/规格列按内容加宽、自动换行、按行数加高行高。
- 打印：`paper_size_code=286`、纵向、fit 1×1、左右 0.2in / 上下 0.4in、`header_str`/`footer_str` 为空。

## 6. 公司设置、学习库与隐私

- 公司设置走 `get_company()` / `save_company(title, buyer)`：
  - 默认读打包的 `data/company.json`；公开版该文件带 `"profile": "public"`。
  - 用户在界面“公司设置”保存后写入 `%LOCALAPPDATA%\Invoice2RKD\company_<profile>.json`
    （公开版是 `company_public.json`，内部版无 profile 时是 `company.json`），不会覆盖安装包里的默认值。
  - `COMPANY` / `BUYER_NAME` 运行时可更新；`excel_writer` 写表时调用 `get_company()` 取标题，所以保存后立即生效。
- 打包时只带 `data/completions.json`，不带公司历史。
- 界面语言设置写入 `%LOCALAPPDATA%\Invoice2RKD\settings.json`（`{"language": "zh"}` 或 `"en"`）。
- 用户点“学习历史入库单”后写入：
  `%LOCALAPPDATA%\Invoice2RKD\catalog_user.json`
- 学习内容：供应商全称、项目名称、规格、单位；用于补全和推断。
- OCR 缓存/预览/日志也都在 `%LOCALAPPDATA%`。
- 仓库 `.gitignore` 已排除真实发票、生成的 xls、`data/catalog.json`、`dist/`。

## 7. 打包

```powershell
powershell -ExecutionPolicy Bypass -File build.ps1
```

关键点：

- `--windowed`：GUI 不弹控制台。
- `--collect-all rapidocr_onnxruntime`：OCR 模型。
- `--collect-all pypdfium2 --collect-binaries pypdfium2_raw`：PDFium DLL。
- `--collect-all pdfplumber --collect-all pdfminer --hidden-import pdfplumber`：文字层解析及 cmap 数据。
- `--collect-all charset_normalizer` + 把 `charset_normalizer\*.pyd` 作为 `--add-binary` 放进包：pdfminer 依赖它。
- `cryptography` 不能排除：pdfminer 的 `pdfdocument.py` 顶层导入它；`clean_dist.py` 也不能删它。
- `--collect-all tkinterdnd2 --hidden-import tkinterdnd2`：拖拽扩展。
- `--collect-all zxingcpp --collect-all cv2`。
- 排除 pandas/openpyxl/lxml/certifi/urllib3 等无用依赖，减小体积。
- `tools/rename_dist.py` 把 `dist/Invoice2RKD` 改成 `dist/入库单生成器`。
- `tools/clean_dist.py` 删除无用目录/DLL；改依赖后请重新验证 exe。
- 打包后必须用 exe 跑一张电子票并加 `--json` 看日志：
  - 正常应是 `... [text]`；
  - 如果出现 `未安装/无法加载 pdfplumber` 或 `[ocr]`，说明文字层依赖打包不完整，不要发布。

## 9. 扩展建议

- 新发票版式：先用调试脚本打印 OCR box（x/y/text），确认表头/合计行/名称/规格/数量/单价的坐标，再在 `get_headers()`/`parse_invoice()` 加规则；优先用通用推断，不要写死某一家供应商。
- 表格线识别：如果 OCR 粘连严重，可以加 OpenCV 形态学找表格线，再按单元格 crop OCR。
- 视觉模型：如果允许联网/API，可以把“看图录入”替换为视觉大模型；当前版本坚持离线。
- 打印模板：把列宽/行高/字体做成配置，适配更多纸型。
